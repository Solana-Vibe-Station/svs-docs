# OpenAPI Specs

This folder contains the OpenAPI 3.0.3 specifications consumed by the GitBook
docs site. Each JSON-RPC method has its own self-contained spec file, so the
displayed HTTP path on every method page exactly matches the production path.

## Layout

```
api-specs/
├── svs-api.yaml                      # 4 SVS-proprietary REST endpoints
├── solana-rpc/                       # 52 Solana JSON-RPC methods (HTTP)
│   ├── getAccountInfo.yaml           #   each spec has one POST / operation
│   ├── getBalance.yaml
│   └── …
├── historical/                       # 10 historical JSON-RPC methods
│   ├── getBlock.yaml                 #   each spec has one POST /historical operation
│   ├── getTransactionsForAddress.yaml
│   └── …
├── websocket-rpc/                    # 16 Solana WebSocket subscription methods
│   ├── accountSubscribe.yaml         #   each spec has one POST / op against wss://
│   ├── slotSubscribe.yaml            #   the JSON-RPC envelope is sent in a WS frame
│   └── …
├── lightspeed/                       # Low-latency transaction landing
│   └── lightspeed.yaml               #   POST /lightspeed (sendTransaction)
└── jito/                             # Jito bundle methods
    ├── sendBundle.yaml               #   POST /jito (Staked tiers only)
    └── simulateBundle.yaml           #   POST / (read-only, all tiers)
```

## Why one file per method

OpenAPI 3.0 keys operations off `(path, verb)` and forbids duplicates. JSON-RPC
APIs (Solana, Ethereum, Bitcoin, etc.) collapse every "method" onto a single
HTTP endpoint with the method name in the request body, which directly
conflicts with that uniqueness rule.

Splitting each method into its own spec file is the most faithful workaround:
- Every spec contains exactly one operation, so the path uniqueness rule is
  trivially satisfied.
- The displayed path on each method's docs page is the *real* production path
  (`/`, `/historical`, etc.), with no fake per-method path or fragment hack.
- Each method renders as its own embeddable OpenAPI block in GitBook.

## Editing

**Don't hand-edit the generated YAML.** Each file ends with the comment

```yaml
# Generated by scripts/generate-rpc-specs.py — edit the generator, not this file.
```

To change a method (description, params, examples, code samples, etc.), edit
its definition in `scripts/generate-rpc-specs.py` and regenerate:

```bash
python3 scripts/generate-rpc-specs.py api-specs
```

The generator is also responsible for the layout of this directory — adding a
new method to the appropriate `_METHODS` list automatically produces a new
`<methodName>.yaml` file in the right subdirectory.

The `svs-api.yaml`, `lightspeed/lightspeed.yaml`, `jito/sendBundle.yaml`, and
`jito/simulateBundle.yaml` specs are the exceptions: they're hand-authored
because they document either a real REST API (svs-api) or transaction-sending
endpoints whose shapes don't fit the standard JSON-RPC method pattern. None of
these are emitted by the generator; edit the YAML directly.

## Connecting to GitBook

In your GitBook space, register each spec as its own OpenAPI source via
**Sidebar → OpenAPI → Add specification → URL**, pointed at the raw GitHub URL
for the file. For example:

```
https://raw.githubusercontent.com/<owner>/svs-docs/main/api-specs/solana-rpc/getBalance.yaml
```

Then embed the operation in any markdown page with a single block:

```
{% openapi-operation spec="solanaRpcGetBalance" path="/" method="post" %}
{% endopenapi-operation %}
```
